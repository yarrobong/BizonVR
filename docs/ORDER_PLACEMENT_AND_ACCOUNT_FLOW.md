# Оформление заказа и аккаунт: целевой сценарий

Дата фиксации: 2026-03-10

## Зачем нужен документ

Этот документ фиксирует целевой пользовательский сценарий для интернет-магазина VR-техники BizonVR и служит единым ТЗ для:

- дизайнера интерфейсов;
- разработчика оформления заказа, аккаунтов и уведомлений;
- владельца продукта при согласовании бизнес-правил.

Документ опирается на текущую кодовую базу и явно отделяет:

- что уже реализовано;
- что нужно поменять;
- что является обязательным для MVP;
- что можно внедрять поэтапно.

## Главный принцип

Основной сценарий должен быть таким:

- пользователь может оформить заказ без регистрации;
- регистрация не блокирует оформление заказа;
- основной сценарий регистрации и входа в аккаунт: `email + код`;
- альтернативный сценарий регистрации и входа: `телефон + SMS-код`;
- вход по паролю доступен только как дополнительный сценарий после того, как пользователь уже вошёл и задал пароль;
- email является обязательным каналом сервисных уведомлений;
- телефон является обязательным каналом связи по заказу;
- подтверждение контактов не требуется для самого заказа;
- подтверждение контактов требуется для аккаунта и чувствительных действий.

Короткая формула:

`Заказ как гость -> email обязателен -> телефон обязателен -> аккаунт по желанию -> основной вход по email-коду -> телефон как альтернатива -> пароль только как дополнительный способ -> подтверждение контактов только для аккаунта и важных действий.`

## Целевая схема аутентификации

Регистрация:

- `Email + код` — основной сценарий;
- `Телефон + SMS-код` — альтернативный сценарий.

Вход:

- `Email + код` — основной сценарий;
- `Email + пароль` — дополнительный сценарий для аккаунтов, где пароль уже задан;
- `Телефон + SMS-код` — запасной и альтернативный сценарий.

После регистрации:

- если пользователь вошёл через телефон, система мягко просит добавить email как резервный канал и как основной канал уведомлений по заказам;
- если пользователь вошёл через email, система может предложить добавить телефон как резервный контакт и канал для важных SMS;
- каждый новый email или телефон сначала подтверждается кодом или ссылкой и только потом используется для входа, восстановления доступа и уведомлений.

## Текущее состояние проекта

По состоянию на 2026-03-13 в проекте уже реализовано следующее:

- экран оформления заказа в [orders/views/checkout.py](../orders/views/checkout.py) открыт и для гостя, и для авторизованного пользователя;
- заказ можно оформить без регистрации, а guest-заказ получает защищённый URL по токену;
- вход в [accounts/views/auth.py](../accounts/views/auth.py) поддерживает три сценария: телефон + SMS, email + пароль, email + одноразовый код;
- подтверждённые логины и подтверждение email в профиле автоматически привязывают подходящие guest-заказы к аккаунту;
- lifecycle заказа и статус оплаты разделены в [orders/models.py](../orders/models.py);
- сервисные уведомления по заказам отправляются через email всегда, а SMS фильтруются по пользовательской настройке;
- в [accounts/views/profile.py](../accounts/views/profile.py) есть раздел уведомлений с persistent-настройками каналов.
- checkout остаётся одной серверной страницей, но уже разбит на шаги `Контакты -> Доставка -> Получатель -> Оплата -> Проверка`;
- публичный auth entrypoint уже переключён на два таба `Email` и `Телефон`, где `Email` открыт по умолчанию.

В коде, маршрутах и именах файлов технический термин `checkout` пока сохранён.

Оставшиеся ограничения текущей поставки:

- оформление заказа остаётся одной серверной страницей, а не многоэкранным route-based wizard flow;
- онлайн-эквайринг и альтернативные платёжные методы не расширялись в этой фазе;
- центр уведомлений пока не хранит user-facing историю отправок, только delivery log.

## Целевой пользовательский путь

### 1. Вход на сайт

Если пользователь не авторизован:

- кнопка в шапке: `Войти` или `Вход / Регистрация`;
- кнопка ведёт на единый экран входа и регистрации, а не на набор из трёх равных сценариев.

Если пользователь авторизован:

- кнопка в шапке: `Личный кабинет`.

### 2. Карточка товара

При нажатии `Добавить в корзину`:

- товар добавляется в корзину;
- показывается уведомление `Товар добавлен в корзину`;
- в уведомлении есть кнопки `Перейти в корзину` и `Продолжить покупки`.

### 3. Корзина

В корзине пользователь видит:

- товары;
- фото;
- название;
- цену;
- количество;
- итог по позиции;
- общую сумму;
- доставку: предварительная стоимость или текст `Стоимость доставки рассчитывается при оформлении`;
- кнопку `Оформить заказ`.

Корзина не должна требовать логина.

В зоне входа перед оформлением заказа показываются два действия:

- `Оформить без регистрации` — основной CTA;
- `Войти / создать аккаунт` — вторичный CTA, который открывает единый auth-экран.

### 4. Экран входа и регистрации

На первом экране не должно быть трёх равных вариантов входа.

Нужны два таба:

- `Email`;
- `Телефон`.

По умолчанию открывается вкладка `Email`.

#### Вкладка Email

Базовый сценарий:

- пользователь вводит email;
- получает одноразовый код;
- вводит код;
- аккаунт создаётся автоматически или выполняется вход.

Во вкладке `Email` есть secondary-переключатель:

- `Войти по коду`;
- `Войти по паролю`.

После первого успешного входа по email-коду можно показать мягкое предложение:

- `Создать пароль для быстрого входа с этого устройства`;
- `Добавить телефон как резервный канал`.

#### Вкладка Телефон

Сценарий:

- пользователь вводит номер телефона;
- получает SMS-код;
- вводит код;
- аккаунт создаётся автоматически или выполняется вход.

После первого успешного входа по телефону система мягко просит:

- добавить email как резервный канал восстановления;
- использовать email для уведомлений по заказам.

### 5. Оформление заказа

Рекомендуемый формат: пошаговое оформление заказа.

Минимальный состав шагов:

1. Контакты
2. Способ получения
3. Получатель
4. Оплата
5. Проверка заказа

## Детализация шагов оформления заказа

### Шаг 1. Контакты

Поля:

- `Имя` — обязательно;
- `Телефон` — обязательно;
- `Email` — обязательно.

Правила:

- email валидируется по формату;
- телефон валидируется по формату;
- email не подтверждается до заказа;
- телефон не подтверждается до заказа;
- рядом может быть мягкий блок `Сохранить данные и создать аккаунт?`.

Для создания аккаунта из оформления заказа рекомендуется сценарий без пароля:

- пользователь нажимает `Создать аккаунт`;
- по умолчанию система предлагает `Email` и отправляет код на email;
- альтернативно пользователь может выбрать `Телефон` и получить SMS-код;
- после подтверждения создаёт аккаунт;
- пароль можно задать позже в личном кабинете.

### Шаг 2. Способ получения

Варианты получения:

- курьер;
- транспортная компания / почта;
- самовывоз;
- по договорённости.

Если доставка:

- страна;
- город;
- улица;
- дом;
- квартира / офис;
- индекс;
- комментарий.

Если ПВЗ:

- город;
- выбранный пункт выдачи.

Если самовывоз:

- адрес точки;
- часы работы;
- текст `После подтверждения заказа с вами свяжутся`.

### Шаг 3. Получатель

Показывается переключатель:

- `Получатель совпадает с покупателем`;
- `Другой получатель`.

Если выбран другой получатель:

- ФИО получателя;
- телефон получателя.

### Шаг 4. Оплата

Показываются доступные способы оплаты:

- онлайн на сайте;
- переводом;
- по счёту;
- при получении, если разрешено.

Дополнительно допускаются условия:

- полная оплата;
- предоплата;
- частичная оплата.

На шаге обязательно видны:

- стоимость товаров;
- скидка;
- доставка;
- итог;
- условия оплаты;
- срок поставки или отправки.

### Шаг 5. Проверка заказа

Пользователь видит итоговую сводку:

- товары;
- количество;
- цена;
- контакты;
- способ доставки;
- адрес;
- способ оплаты;
- комментарий;
- итоговая сумма.

Внизу:

- чекбокс согласия с обработкой персональных данных;
- чекбокс согласия с офертой / условиями продажи;
- кнопка `Оформить заказ`, `Подтвердить и перейти к оплате` или `Оформить заказ и оплатить`.

## Логика после подтверждения заказа

### Если оплата онлайн

- создаётся заказ;
- заказ получает номер;
- пользователь перенаправляется на страницу оплаты;
- после оплаты попадает на страницу благодарности или на страницу заказа со статусом оплаты.

### Если оплата не онлайн

- создаётся заказ;
- пользователь попадает на страницу `Заказ принят`;
- на странице показываются номер заказа, состав, контакты и следующий шаг.

## Подтверждение контактов

### Что не нужно подтверждать до заказа

- email;
- телефон.

### Когда email подтверждается обязательно

- при создании аккаунта;
- при добавлении email после регистрации по телефону;
- при смене email в личном кабинете;
- при восстановлении доступа через email.

### Когда телефон подтверждается обязательно

- при входе по SMS-коду;
- при добавлении телефона после регистрации по email;
- при создании аккаунта через телефон;
- при смене телефона;
- при чувствительных действиях, если усиление безопасности нужно отдельно.

## Уведомления

### Email

Email является обязательным сервисным каналом.

Обязательные письма:

1. Заказ оформлен
2. Оплата получена
3. Заказ подтверждён магазином
4. Заказ передан в доставку
5. Заказ доставлен или готов к выдаче
6. Заказ отменён
7. Возврат, обмен или изменение заказа

Содержимое письма о создании заказа:

- номер заказа;
- состав заказа;
- сумма;
- способ доставки;
- способ оплаты;
- контакты магазина;
- что будет дальше.

### SMS

SMS используется только для важных событий и кодов.

Рекомендуемые SMS-события:

- заказ принят;
- заказ подтверждён;
- заказ отправлен;
- заказ готов к выдаче;
- нужен контакт с клиентом;
- вход по коду;
- подтверждение телефона.

## Оформление заказа как гость

Это обязательный сценарий.

Поведение:

- пользователь вводит имя, телефон и email;
- оформляет заказ без регистрации;
- получает email-уведомление;
- после заказа видит предложение `Создать аккаунт, чтобы отслеживать заказ быстрее`.

Если пользователь соглашается:

- по умолчанию используется уже введённый email и отправляется email-код;
- альтернативно пользователь может выбрать телефон и получить SMS-код;
- отправляется код подтверждения;
- после подтверждения создаётся аккаунт;
- ранее созданный guest order привязывается к аккаунту.

## Личный кабинет

После входа пользователь должен видеть разделы:

- Мои заказы;
- Детали заказа;
- Мои данные;
- Адреса доставки;
- Способы оплаты;
- Уведомления;
- Избранное;
- Гарантия / сервис / возвраты.

В профиле должны отображаться:

- имя;
- телефон;
- email;
- статус `Email подтверждён / не подтверждён`;
- статус `Телефон подтверждён / не подтверждён`.

После первого входа дополнительно нужны мягкие продуктовые подсказки:

- для email-регистрации: предложить добавить телефон;
- для phone-регистрации: предложить добавить email;
- не блокировать личный кабинет, если пользователь пропускает эти шаги.

В настройках уведомлений:

- email по заказам;
- SMS по важным статусам;
- маркетинговые рассылки;
- уведомления о наличии товара.

### Безопасность аутентификации

Обязательные требования независимо от выбранного UI:

- одинаковые сообщения об ошибке на логине, регистрации, отправке кода и восстановлении доступа, чтобы не раскрывать существование аккаунта;
- throttling на отправку кодов и попытки входа по email, телефону, IP и сессии;
- повторная отправка кода не чаще одного раза примерно в 30 секунд с дальнейшим наращиванием задержки при злоупотреблении;
- reauthentication для чувствительных действий: смена email, смена телефона, установка или смена пароля, восстановление доступа;
- пароли хранятся только в виде безопасного хеша; предпочтительный алгоритм для целевого состояния — Argon2id;
- новый контакт нельзя использовать как логин, recovery-канал или канал уведомлений, пока он не подтверждён.

## Что не рекомендуется

Нельзя делать обязательным до оформления заказа:

- создание пароля;
- подтверждение email;
- подтверждение телефона.

Нежелательные варианты:

- только телефон как единый способ входа;
- только пароль как обязательная основа входа;
- только email без резервного канала для пользователя, который уже готов добавить второй контакт;
- обязательная регистрация перед оформлением заказа.

## Краткая бизнес-формулировка

Пользователь может оформить заказ без регистрации.

Для заказа обязательны:

- имя;
- телефон;
- email.

Email является обязательным каналом сервисных уведомлений.

Телефон используется для связи и SMS по важным статусам.

Подтверждение email и телефона не требуется для оформления заказа.

Основной вход и регистрация строятся вокруг `email + код`.

`Телефон + SMS-код` остаётся альтернативным сценарием.

`Email + пароль` доступен только после того, как пользователь уже вошёл и задал пароль.

Подтверждение email и телефона требуется для регистрации аккаунта, входа по коду, смены контактов и восстановления доступа.

После оформления заказа гостю предлагается создать аккаунт на основе введённых контактов.

После подтверждения контакта ранее созданные guest orders должны привязываться к аккаунту.

В личном кабинете должны отображаться статусы подтверждения email и телефона, а также настройки каналов уведомлений.
