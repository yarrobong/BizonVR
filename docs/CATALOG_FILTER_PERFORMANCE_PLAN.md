# План стабилизации и ускорения фильтров каталога

Актуально для текущего рабочего дерева BizonVR на 2026-04-27.

Этот документ фиксирует:

- что именно наблюдалось на продакшене;
- почему каталоговые фильтры являются вероятным источником деградации;
- какие меры нужны для быстрого восстановления;
- какой поэтапный план даст устойчивое ускорение без поломки публичного каталога.

Документ дополняет [CATALOG_FILTERS_AUDIT.md](/Users/Yaroslav/Documents/dev/BizonVR/docs/CATALOG_FILTERS_AUDIT.md): аудит описывает текущее устройство системы, а этот файл описывает план устранения деградации производительности.

## Короткий вывод

На продакшене наблюдался не “падёж процесса”, а starvation Gunicorn-воркеров:

- `nginx` и TLS были живы;
- PostgreSQL отвечал и не показывал блокировок;
- `gunicorn` был поднят, но работал с `2` sync-воркерами;
- тяжёлые запросы к каталогу занимали оба воркера;
- после этого даже `/`, `/admin` и `/favicon.ico` начинали получать `upstream timed out`, потому что им было некому ответить.

Наиболее вероятный триггер деградации сейчас:

- дорогие live-подсчёты фильтров в [catalog/filtering.py](/Users/Yaroslav/Documents/dev/BizonVR/catalog/filtering.py);
- многократная пересборка почти одинаковых queryset-ов в [catalog/views/products.py](/Users/Yaroslav/Documents/dev/BizonVR/catalog/views/products.py);
- тяжёлые `JOIN + DISTINCT + GROUP BY + aggregate` по `ProductCharacteristic`, `ProductTag`, `ProductStock`;
- низкая пропускная способность из-за `2` sync-воркеров;
- длинные или шумные query string с повторяющимися параметрами на `/catalog/`.

## Что уже подтверждено

По продовой диагностике подтверждено следующее:

- `curl` до `127.0.0.1:8000` зависал без ответа;
- `nginx` писал `upstream timed out`;
- PostgreSQL отвечал на `select 1`;
- блокировок по `pg_blocking_pids` не было;
- `strace` на воркере показывал SQL с полями `category_id`, `category__section__slug`, `total`;
- этот паттерн соответствует коду `get_category_and_section_counts()` в [catalog/filtering.py](/Users/Yaroslav/Documents/dev/BizonVR/catalog/filtering.py).

Следствие:

- проблема не выглядит как сетевой отказ, crash PostgreSQL или общий deadlock в БД;
- проблема выглядит как слишком дорогая обработка запросов каталога внутри Django.

## Почему текущая реализация тяжёлая

### 1. Один HTTP-запрос каталога запускает серию тяжёлых вычислений

В [catalog/views/products.py](/Users/Yaroslav/Documents/dev/BizonVR/catalog/views/products.py) каталоговый view не ограничивается получением списка товаров.

Во время `get_context_data()` дополнительно вызываются:

- `get_price_bounds()`
- `get_product_tags()`
- `get_characteristics_context()`
- `get_category_and_section_counts()`
- `applied_qs.count()`

Это означает, что один рендер `/catalog/` фактически делает несколько отдельных больших SQL-обходов по той же выборке.

### 2. База фильтра многократно собирается заново

В [catalog/filtering.py](/Users/Yaroslav/Documents/dev/BizonVR/catalog/filtering.py) методы:

- `build_product_filter_queryset()`
- `build_bundle_filter_queryset()`
- `build_filter_queryset()`

используются повторно почти каждым вспомогательным подсчётом.

Следствие:

- один и тот же набор фильтров и join-ов пересобирается снова и снова;
- итоговая стоимость страницы складывается не из одного дорогого SQL, а из серии похожих дорогих SQL.

### 3. Сам queryset уже дорогой ещё до побочных подсчётов

Для обычного product mode текущая база включает:

- фильтрацию по `section` и `category`;
- фильтрацию по `tags`;
- фильтрацию по `characteristics`;
- аннотацию `catalog_stock_total=Sum('stocks__quantity')`;
- аннотацию `catalog_effective_price`;
- ценовые фильтры;
- `distinct()`.

Комбинация `JOIN` по остаткам, тегам и характеристикам плюс `aggregate` и `distinct()` обычно плохо масштабируется на больших таблицах.

### 4. Подсчёты counts по категориям и секциям дорогие сами по себе

В [catalog/filtering.py](/Users/Yaroslav/Documents/dev/BizonVR/catalog/filtering.py) `get_category_and_section_counts()` строит выборки вида:

- `values('category_id', 'category__section__slug')`
- `annotate(total=Count('id', distinct=True))`

Причём отдельно для товаров и отдельно для наборов.

Это дорого потому что:

- запросу нужно сначала получить фильтрованный набор;
- затем выполнить группировку;
- затем считать `distinct` по сущностям;
- затем повторить это для bundle mode.

Именно этот запрос уже был замечен на проде через `strace`.

### 5. Характеристические фильтры особенно дорогие

В managed-режиме [catalog/filtering.py](/Users/Yaroslav/Documents/dev/BizonVR/catalog/filtering.py) для каждой `FilterConfig` строится отдельная группа значений.

Это даёт:

- отдельный `scoped_qs`;
- отдельную выборку `ProductCharacteristic`;
- склейку raw values в normalized buckets;
- distinct count по entity id;
- сортировку и построение URL.

В legacy-режиме ситуация не легче:

- либо выполняется широкий `GROUP BY name, value`;
- либо после появления активных `char_*` выполняется серия отдельных запросов по каждому `char_name`.

Следствие:

- фильтры характеристик являются самым вероятным источником взрывного роста времени ответа при большом каталоге.

### 6. Нет очевидных составных индексов под основные фильтрационные паттерны

В [catalog/models.py](/Users/Yaroslav/Documents/dev/BizonVR/catalog/models.py) у `ProductCharacteristic` сейчас нет явных составных индексов под частые операции:

- поиск по `product`;
- фильтрация по `name`;
- фильтрация по `name + value`;
- выборки `product__in ... and name=value`.

Для фильтрационного ядра это важная дырка.

Дополнительно у `ProductStock` нет явного отдельного индекса под типовые агрегации:

- `product_id`
- `product_id + variant_id`

Уникальный constraint по `product + pickup_point + variant` помогает не всем read-path запросам.

### 7. Система слишком чувствительна к шумным query string

В продовых логах уже встречался аномальный URL `/catalog/` с длинной строкой параметров и многократными повторами.

Даже если код логически обрабатывает такой URL корректно, он:

- увеличивает размер запроса;
- может провоцировать лишние разборы параметров;
- повышает вероятность тяжёлых комбинаций фильтров;
- создаёт лёгкую цель для бот-нагрузки;
- при `2` sync-воркерах быстро выжигает всю пропускную способность.

## Цели плана

### Цель 1. Быстро стабилизировать прод

Нужно добиться, чтобы даже при тяжёлом `/catalog/` не падала доступность всего сайта.

### Цель 2. Сильно сократить стоимость одного запроса каталога

Нужно уменьшить число повторных queryset-ов и стоимость live-подсчётов.

### Цель 3. Упростить эксплуатацию

Нужны метрики, понятная диагностика и защитные лимиты, чтобы такие инциденты выявлялись до того, как “ложится сайт”.

## План работ

## Этап 0. Аварийная стабилизация продакшена

Цель этапа: снизить вероятность полного starvation до исправлений в коде.

### 0.1. Увеличить число воркеров Gunicorn

Минимальная мера:

- поднять `GUNICORN_WORKERS` с `2` до `4`.

Лучше одновременно:

- задать разумный `--timeout`;
- убедиться, что сервис стартует из проектного `.venv`, а не из глобального Python;
- не держать сервис от `root`, если нет специальных причин.

Ожидаемый эффект:

- один-два тяжёлых каталоговых запроса перестанут моментально убивать весь сайт;
- возрастёт запас по конкурентности.

### 0.2. Ввести rate limiting на каталог в Nginx

Нужно ограничить:

- частоту запросов на `/catalog/`;
- аномально длинные query string;
- повторяющиеся burst-запросы с одного IP;
- при необходимости отдельно ограничить ботовые UA.

Ожидаемый эффект:

- шумовые и бот-запросы перестанут безнаказанно занимать все воркеры.

### 0.3. Добавить базовую защиту на уровне query params

Нужна серверная нормализация:

- ограничить длину query string;
- ограничить число `char_*` параметров;
- ограничить число повторов одного и того же ключа;
- дедуплицировать значения `section`, `category`, `tag`, `char_*`.

Если запрос не проходит лимиты:

- мягко обрезать лишнее;
- или возвращать `400` для явно мусорных комбинаций.

### 0.4. Включить наблюдаемость по медленным запросам

Нужно логировать:

- путь;
- query string;
- длительность;
- число SQL-запросов;
- суммарное время SQL;
- режим фильтров `legacy/category/section`;
- количество characteristic groups.

Без этого после стабилизации мы снова будем диагностировать почти вслепую.

## Этап 1. Замеры и профилирование

Цель этапа: зафиксировать реальную стоимость каждого подэтапа страницы каталога.

### 1.1. Профилировать `ProductListView.get_context_data()`

Нужно замерить отдельно:

- `get_queryset()`
- `get_price_bounds()`
- `get_product_tags()`
- `get_characteristics_context()`
- `get_category_and_section_counts()`
- `applied_qs.count()`

Нужно получить ответ на вопрос:

- где самый дорогой участок при пустом каталоге;
- где самый дорогой участок при `q`, `tag`, `price`, `char_*`;
- где самый дорогой участок при bundle mode.

### 1.2. Снять `EXPLAIN ANALYZE` по главным SQL

Нужно сохранить реальные планы для:

- списка товаров;
- counts по категориям и секциям;
- price bounds;
- tags;
- characteristic groups.

Особое внимание:

- `HashAggregate`;
- `GroupAggregate`;
- `Nested Loop`;
- `Bitmap Heap Scan`;
- `Sort`;
- recheck из-за `distinct`.

### 1.3. Включить `pg_stat_statements`

Нужно получить:

- самые дорогие SQL по total time;
- самые дорогие SQL по mean time;
- самые частые SQL каталога;
- планы до и после оптимизаций.

## Этап 2. Быстрые оптимизации с низким риском

Цель этапа: дать заметный выигрыш без глубокого переписывания фильтрационного ядра.

### 2.1. Кэшировать derived data по нормализованной query string

Кандидаты на кэш в первую очередь:

- `get_price_bounds()`
- `get_product_tags()`
- `get_category_and_section_counts()`
- `get_characteristics_context()`

Ключ кэша должен строиться из:

- нормализованных `section/category/tag`;
- `price_min/price_max`;
- `q`;
- canonical `char_*`;
- режима `bundle/product`.

Важно:

- использовать именно нормализованный набор параметров, а не сырой query string;
- ставить короткий TTL;
- уметь инвалидировать кэш при изменении каталога.

### 2.2. Не выполнять тяжёлые блоки, если они не нужны

Нужно добавить прагматичные short-circuit правила:

- если выдача пуста, не строить часть secondary-фильтров полностью;
- если на scope нет managed-конфигов и legacy-группы слишком шумные, не показывать их целиком;
- если есть search query, можно деградировать часть counts и heavy facets.

### 2.3. Сократить повторную пересборку queryset-ов

Нужно найти точки, где один и тот же базовый queryset строится многократно, и:

- переиспользовать общую базу;
- выносить общие части в один helper;
- по возможности оперировать списком `product_id`, а не снова и снова собирать широкий queryset.

### 2.4. Ограничить legacy fallback

Legacy-режим сейчас безопасен функционально, но дорог вычислительно.

Нужно ввести ограничения:

- лимит на число групп;
- лимит на число значений в группе;
- ранний выход для характеристик с высоким cardinality;
- возможно скрывать часть legacy-характеристик под дополнительным действием пользователя.

## Этап 3. Оптимизация SQL и структуры вычислений

Цель этапа: убрать системную дороговизну, а не только прикрыть её кэшем.

### 3.1. Пересмотреть стратегию `distinct()`

Сейчас многие queryset-ы доходят до `.distinct()` после серии `JOIN`.

Нужно проверить, где можно заменить:

- `JOIN + DISTINCT`
- на `Exists`
- или на фильтрацию по подзапросу `id__in`
- или на двухшаговый подход “получить id -> агрегировать по id”.

Особенно это важно для фильтрации по характеристикам и тегам.

### 3.2. Разделить listing-query и facet-query

Сейчас логика выдачи и логика facet-подсчётов тесно переплетены.

Нужно разнести:

- queryset списка товаров;
- queryset для price bounds;
- queryset для tags;
- queryset для category/section counts;
- queryset для characteristic options.

Каждый из них должен строиться осознанно под свою задачу, а не наследовать всю тяжесть соседних расчётов.

### 3.3. Оптимизировать characteristic filtering

Нужно проверить, где лучше перейти на:

- работу через предварительно отфильтрованный набор `product_id`;
- агрегаты по `ProductCharacteristic` поверх ограниченного списка id;
- меньшее количество повторных `distinct`;
- canonical storage для normalized values, чтобы не склеивать их заново на каждом запросе.

### 3.4. Упростить counts по категориям и секциям

`get_category_and_section_counts()` сейчас выглядит как один из самых подозрительных участков.

Возможные упрощения:

- считать counts только для видимых scope, а не всего дерева;
- кешировать по query;
- при search query выключать counts или показывать только текущий scope;
- считать counts по уже вычисленному списку id, а не повторно по широкому queryset.

### 3.5. Упростить tags facet

`get_product_tags()` сейчас строится от фильтрованной выборки.

Нужно проверить:

- нужен ли полный live count у тегов всегда;
- можно ли считать теги только для top scope;
- можно ли кешировать их агрессивнее, чем сейчас.

## Этап 4. Индексы и модельные улучшения

Цель этапа: дать PostgreSQL адекватную опору для основных фильтрационных сценариев.

### 4.1. Индексы для `ProductCharacteristic`

Кандидаты на добавление после проверки `EXPLAIN`:

- `(product, name)`
- `(name, value)`
- `(name, value, product)`

Если фильтрация по `value` часто идёт с `icontains` или похожими lookup-ами, нужно отдельно оценить, не требуется ли другой тип индекса или изменение lookup-стратегии.

### 4.2. Индексы для `ProductStock`

Кандидаты:

- `(product, variant)`
- `(product)`

Особенно полезно для:

- `Sum('stocks__quantity')`
- `_product_stock_totals()`
- `_variant_stock_totals()`

### 4.3. Проверить индексы для связи товаров и тегов

Нужно отдельно проверить through-table `Product.tags.through`:

- хватает ли текущих индексов для `tags__slug`;
- не нужен ли индекс на сторону связи, которая чаще участвует в facet-подсчётах.

## Этап 5. Поведенческие изменения в UI и UX

Цель этапа: не заставлять бэкенд считать всё всегда, если пользователю это не нужно.

### 5.1. Отложенная загрузка тяжёлых фасетов

Хороший компромисс:

- сначала отдавать список товаров и базовые фильтры;
- тяжёлые characteristic groups догружать отдельно;
- или раскрывать их по запросу пользователя.

### 5.2. Деградация counts в режиме поиска

Если пользователь уже ввёл `q`, цена вычисления counts обычно выше пользы.

В search mode допустимо:

- не показывать category/section counts;
- не пересчитывать все characteristic groups;
- показывать упрощённый набор фасетов.

### 5.3. Ограничение high-cardinality характеристик

Некоторые характеристики объективно плохо подходят для live facet filtering.

Нужно уметь:

- не включать их в managed filters;
- не тянуть их в legacy fallback;
- или отдавать их как текстовый поиск, а не как длинный список значений.

## Этап 6. Тесты и критерии приёмки

Цель этапа: сделать ускорение измеримым и не сломать каталог.

### 6.1. Добавить тесты на защиту от шумных query string

Нужны тесты на:

- повтор `section/category/tag`;
- слишком длинные `char_*`;
- мусорные canonical/raw combinations;
- дедупликацию одинаковых фильтров.

### 6.2. Добавить performance smoke tests

Нужны хотя бы базовые проверки:

- каталог без фильтров;
- каталог с `tag`;
- каталог с `q`;
- каталог с `price_min/price_max`;
- каталог с несколькими `char_*`;
- bundle mode.

Эти тесты не обязаны быть micro-benchmark, но должны ловить взрыв числа SQL-запросов и грубые регрессии.

### 6.3. Зафиксировать продуктовые инварианты

До и после оптимизаций должны сохраниться:

- корректность выдачи;
- корректность `managed` и `legacy` fallback;
- совместимость старых `char_*` ссылок;
- корректность `count` там, где он ещё показывается;
- корректность `price bounds`.

## Рекомендуемый порядок внедрения

Если идти по максимально выгодной траектории, порядок такой:

1. Стабилизировать прод: воркеры, rate limit, базовые лимиты на query string.
2. Добавить наблюдаемость и замеры.
3. Закэшировать derived filter data по нормализованной query string.
4. Упростить или временно деградировать самые дорогие live counts.
5. Добавить индексы под подтверждённые тяжелые планы.
6. Переработать characteristic filtering и разделить listing/facets.
7. Добавить UI-ленивую загрузку для тяжёлых фасетов.

## Предлагаемая первая итерация

Если нужно выбрать самый практичный scope на ближайший короткий цикл, он такой:

### Sprint 1

- поднять `gunicorn` до `4` воркеров;
- ограничить `/catalog/` в `nginx`;
- добавить нормализацию и лимиты query params;
- кэшировать `get_category_and_section_counts()`;
- кэшировать `get_price_bounds()`;
- логировать slow catalog requests.

### Sprint 2

- кэшировать `get_product_tags()` и `get_characteristics_context()`;
- добавить индексы на `ProductCharacteristic`;
- упростить legacy fallback;
- отключать часть heavy facets в search mode.

### Sprint 3

- переработать структуру facet-подсчётов;
- перейти к переиспользуемой базе `product_id`;
- убрать лишние `distinct()` и тяжёлые повторные join-ы;
- при необходимости вынести тяжёлые фасеты в отдельную загрузку.

## Критерии успеха

План можно считать успешным, если после внедрения:

- один тяжёлый запрос к `/catalog/` не делает сайт недоступным;
- два параллельных запросa к `/catalog/` не выбивают `/`, `/admin` и статические URL;
- медианное и p95 время ответа каталога заметно снижаются;
- число SQL-запросов на рендер каталога уменьшается;
- наиболее тяжёлые facet-query перестают быть top offender в `pg_stat_statements`;
- шумные и мусорные query string перестают приводить к деградации сервиса.

## Открытые решения перед реализацией

Перед кодовыми изменениями стоит отдельно утвердить:

- допускаем ли временное упрощение UI фасетов ради стабильности;
- можно ли отключать часть counts в search mode;
- хотим ли сохранять полный legacy fallback или лучше сделать его более жёстким;
- готовы ли добавлять Redis-кэш для более предсказуемого shared cache на проде.
