# План запуска SEO-лендингов-презентаций для BizonVR

Актуально для текущего рабочего дерева BizonVR на 2026-04-28.

Этот документ описывает, как превратить идею "статьи-презентации" в управляемую часть сайта BizonVR:

- с сильным SEO-эффектом;
- с привязкой к реальным товарам каталога;
- с очень выразительным дизайном;
- без превращения проекта в тяжёлую CMS.

## Короткий вывод

Идея очень сильная и хорошо ложится на ваш проект.

По сути это должен быть не "блог ради блога", а отдельный слой коммерческих SEO-страниц между каталогом и standalone-лендингами:

- пользователь приходит по запросу вроде `vr для клуба`, `какой vr шлем купить домой`, `vr аттракцион для тц`;
- попадает не в сухой листинг каталога, а в красивую страницу-объяснение;
- получает готовый сценарий выбора, кейсы, сравнение моделей, ответы на типовые вопросы;
- в этой же странице видит 1-3 рекомендованных товара/комплекта и может купить их сразу у вас.

Это действительно может закрывать большую часть однотипных вопросов и одновременно усиливать индексацию.

## Почему это особенно подходит BizonVR

В текущем проекте уже есть почти все базовые кирпичи:

- серверный рендеринг на Django templates;
- живой каталог с товарами, категориями, комплектами и ценами;
- существующие промо-страницы `/arenda/`, `/compact-vr/`, `/invest/`, `/conference-attractions/`;
- `django.contrib.sitemaps` и публичный `sitemap.xml`;
- у товаров уже есть управляемые блоки описания: `ProductContentBlock`, `ProductDescription`, `ProductDescriptionBlock`;
- дизайн сайта уже допускает насыщенные промо-страницы, а не только "сетку товаров".

То есть вам не нужен отдельный WordPress или внешний конструктор. Лучше сделать это внутри текущего Django-проекта.

## Каким должен быть формат страницы

Каждая такая страница должна быть не просто статьёй, а "коммерческой презентацией":

- сильный hero-блок;
- понятный оффер под конкретный интент;
- визуальный сторителлинг;
- сравнение решений;
- блок "кому подходит";
- блок "что входит";
- блок "какие модели рекомендуем";
- FAQ;
- CTA на покупку, консультацию или подбор.

Хороший формат URL:

- `/solutions/vr-dlya-kluba/`
- `/solutions/vr-dlya-doma/`
- `/solutions/vr-attrakcion-dlya-tc/`
- `/solutions/luchshie-vr-shlemy-dlya-detey/`
- `/solutions/kak-otkryt-vr-klub-v-malenkom-gorode/`

Важно: это должны быть не дубли обычных карточек товара, а страницы под интент и сценарий выбора.

## Какие типы страниц стоит делать

Лучше сразу разделить контент на 4 типа.

### 1. Страницы под сегмент

Примеры:

- VR для клубов
- VR для дома
- VR для бизнеса
- VR для мероприятий
- VR-аттракционы для ТЦ

Это самые важные страницы, потому что они отвечают на широкие коммерческие запросы.

### 2. Страницы под задачу

Примеры:

- Какой VR-шлем купить для дома в 2026
- Как выбрать VR-аттракцион для потока посетителей
- Что нужно для запуска компактной VR-арены

Такие страницы хорошо собирают информационный и полукоммерческий трафик.

### 3. Страницы под подборку

Примеры:

- Топ VR-шлемов для дома
- Лучшие VR-решения для клуба
- Популярные VR-аттракционы для аренды и мероприятий

Это удобный мост между SEO и продажами.

### 4. Страницы под готовое решение

Примеры:

- Готовый комплект для VR-клуба на 4 шлема
- Домашний VR-комплект под ключ
- Стартовый набор для выездных VR-мероприятий

Здесь особенно хорошо работают `ProductBundle` и покупка комплекта целиком.

## Рекомендуемая реализация в BizonVR

Лучший путь для проекта сейчас: не отдельный блог и не набор вручную сверстанных html-папок, а новая Django-сущность для SEO-лендингов.

### Вариант, который я рекомендую

Добавить новое приложение или модуль, например `content` или `landing_pages`, с моделью вроде:

- `title`
- `slug`
- `page_type`
- `is_published`
- `h1`
- `meta_title`
- `meta_description`
- `lead`
- `hero_badge`
- `hero_cta_text`
- `hero_cta_url`
- `theme`
- `cover_image`
- `intro`
- `faq_json`
- `seo_text_bottom`
- `products` many-to-many к `Product`
- `bundles` many-to-many к `ProductBundle`
- `categories` many-to-many к `Category`
- `updated_at`

И вторую модель для блочного конструктора страницы, например `LandingPageBlock`:

- `page`
- `block_type`
- `sort_order`
- `is_active`
- `data` JSONField

Типы блоков:

- `hero`
- `metrics`
- `problem_solution`
- `comparison_table`
- `use_cases`
- `product_cards`
- `bundle_offer`
- `gallery`
- `faq`
- `testimonial`
- `final_cta`

Это даст 2 ключевых плюса:

- страницы будут управляться из Django admin;
- дизайн можно сделать очень сочным, но при этом собирать его из повторно используемых секций.

## Почему не стоит делать это просто как папки с html

Сейчас standalone-лендинги в проекте уже есть, но для массового SEO-контента этот подход быстро станет дорогим.

Минусы чисто файлового подхода:

- трудно масштабировать десятки страниц;
- сложно обновлять meta-теги, canonical, schema, блоки FAQ;
- сложно связывать страницы с актуальными товарами и ценами каталога;
- тяжело поддерживать sitemap и админское редактирование;
- высокий риск, что лендинги будут устаревать отдельно от каталога.

Standalone-формат стоит оставить для 1-2 очень особых больших промо-страниц. Для основной SEO-сетки лучше использовать Django-модели и шаблоны.

## Как связать такие страницы с каталогом

Самое важное правило: страница должна продавать не "вообще VR", а конкретные сущности из каталога.

Для этого каждая страница должна уметь показывать:

- 1-3 флагманских товара;
- 1-2 альтернативы;
- готовый комплект;
- карточки категорий;
- CTA "купить сейчас" и "получить консультацию".

Рекомендация по логике:

- основной товар выводить крупным sticky-блоком рядом с ключевыми аргументами;
- ниже давать сравнение 2-4 моделей;
- ещё ниже добавлять секцию "Похожие решения";
- если интент B2B, добавлять заявку на подбор вместо агрессивной кнопки оплаты как единственный CTA.

## SEO-структура

Чтобы страницы реально индексировались и не мешали друг другу, стоит сразу ввести правила.

### Для каждой страницы

- уникальный `title`;
- уникальный `meta description`;
- понятный `H1`;
- `canonical`;
- хлебные крошки;
- `FAQPage` schema там, где есть частые вопросы;
- `ItemList` schema для подборок;
- `Product` schema только если страница завязана на один основной товар;
- включение в `sitemap.xml`.

### Внутренняя перелинковка

- из каталога ссылаться на релевантные SEO-страницы;
- из карточек товара ссылаться на "Как выбрать" и "Для кого подходит";
- с homepage вынести блок "Готовые решения";
- из футера или раздела знаний дать доступ к основным страницам по сегментам.

### Антидубли

Не стоит плодить страницы вроде:

- `vr-dlya-doma`
- `domashnij-vr`
- `kupit-vr-domoj`

если фактически у них один и тот же интент.

Лучше одна сильная посадочная страница на один смысловой кластер.

## Дизайн: каким сделать "сочный" стиль

Если делать такие страницы, их нельзя оформлять как обычный блог с белым фоном и скучным текстом.

Для BizonVR лучше подойдёт формат "premium tech showcase":

- крупный hero с ярким фокусом на продукт;
- сложный фон: градиенты, glow, сетки, мягкие шумы, light-spots;
- выраженная типографика для заголовков;
- чередование тёмных и светлых секций;
- карточки с depth-эффектом;
- реальные фото/рендеры оборудования;
- блоки с цифрами, сценариями, кейсами;
- sticky CTA с ценой или заявкой;
- анимации появления секций, но без перегруза.

### Важный принцип

Нужна не "одна универсальная тема на всё", а 3-4 визуальных режима:

- `home-tech` для домашних решений;
- `club-pro` для клубов и бизнеса;
- `attraction-energy` для аттракционов и event-направления;
- `invest-premium` для инвестиционных или B2B-страниц.

То есть движок страниц должен быть общий, а визуальная тема переключаемая через поле `theme`.

## Как это собрать технически без боли

Самый прагматичный путь:

### Этап 1. MVP без отдельного rich CMS

Сделать:

- модель `LandingPage`;
- модель `LandingPageBlock`;
- 1 шаблон `templates/landing_pages/detail.html`;
- 6-8 переиспользуемых partials для разных секций;
- `DetailView` по `slug`;
- включение страниц в sitemap;
- админку с сортировкой блоков.

На этом этапе можно выпустить первые страницы:

- VR для дома
- VR для клуба
- VR-аттракционы для мероприятий
- Готовый комплект для запуска VR-зоны

### Этап 2. Коммерческая связка с каталогом

Добавить:

- блоки связанных товаров;
- блоки связанных комплектов;
- блок сравнения моделей;
- блок FAQ;
- форму заявки с legal consent;
- события аналитики на CTA.

### Этап 3. Контент-система

Добавить:

- список всех страниц `/solutions/`;
- фильтрацию по теме;
- блок "похожие решения";
- шаблоны страниц под разные интенты;
- JSON-LD schema генерацию;
- preview в админке.

## Как админ будет собирать такие страницы

Ключевой принцип: админ не должен "дизайнить страницу руками".

Нельзя заставлять контент-менеджера:

- писать CSS;
- двигать блоки через произвольные grid-настройки;
- вставлять сырой HTML для каждой секции;
- вручную собирать accordion, иконки и карточки товаров;
- помнить технические правила по отступам, адаптиву и schema.

Правильная модель другая:

- дизайнер/разработчик один раз создаёт библиотеку секций;
- админ собирает страницу из готовых блоков;
- система жёстко ограничивает опасные решения;
- итог всё равно выглядит "сочно", потому что вариативность заложена заранее.

### Что именно должен делать админ

У администратора должны быть 3 уровня работы:

1. Настройки страницы.
2. Сборка блоков.
3. Подбор контента и товаров.

### 1. Настройки страницы

На уровне самой страницы админ заполняет:

- название страницы;
- slug;
- тип страницы;
- статус публикации;
- `H1`;
- `title`;
- `meta description`;
- визуальную тему;
- основной CTA;
- товары и комплекты, которые надо продвигать;
- обложку/hero media.

То есть админ отвечает за смысл и контент, а не за низкоуровневую верстку.

### 2. Сборка блоков

Дальше админ работает с повторяемыми секциями:

- `Hero`
- `Преимущества`
- `Сценарии использования`
- `Сравнение моделей`
- `Подборка товаров`
- `FAQ`
- `Отзывы`
- `Финальный CTA`

Каждый блок добавляется как отдельная запись с типом и порядком.

Это хорошо совпадает с тем, как у вас уже устроены `ProductContentBlock`, `ProductDescriptionBlock` и сортируемые inline в админке.

### 3. Подбор контента и товаров

Внутри каждого блока админ должен выбирать:

- текст;
- изображения;
- иконки;
- стиль секции из ограниченного списка;
- связанные товары;
- варианты кнопок;
- вариант расположения контента.

Но не должен задавать произвольные CSS-классы.

## Как сделать админку удобной, а не страшной

Лучший UX для редактора: не raw JSON, а управляемые формы по типу блока.

### Что не стоит делать

Плохой вариант:

- одно поле `data = JSONField`;
- редактор сам пишет туда структуру вручную.

Это удобно разработчику, но неудобно бизнесу и легко ломается.

### Что стоит делать

Хороший вариант:

- у каждого типа блока свой набор полей;
- в админке показываются только релевантные поля;
- есть help text, превью и ограничения;
- порядок блоков меняется drag-and-drop.

Например:

#### Hero block

Поля:

- eyebrow / badge;
- заголовок;
- подзаголовок;
- фон;
- desktop image;
- mobile image;
- видео или анимированный фон;
- primary CTA;
- secondary CTA;
- вариант расположения: `left`, `center`, `split`;
- визуальный режим: `light-glow`, `dark-tech`, `showcase`.

#### FAQ block

Поля:

- заголовок секции;
- intro text;
- список вопросов и ответов;
- стиль раскрытия: `minimal`, `card`, `bordered`.

Редактор не думает, как писать JS-accordion. Он просто добавляет пары вопрос-ответ.

#### Product showcase block

Поля:

- заголовок;
- подпись;
- связанные товары;
- показывать ли цену;
- показывать ли старую цену/экономию;
- стиль карточек: `compact`, `premium`, `comparison`;
- CTA-кнопка.

#### Metrics / benefits block

Поля:

- заголовок;
- список тезисов;
- иконка для каждого тезиса;
- цветовая схема;
- количество колонок.

## Как учесть hero-картинки, SVG, FAQ и прочие детали

Нужно не давать админу "всё подряд", а превратить это в управляемую библиотеку.

### Hero-картинки

Для hero лучше держать отдельные поля:

- `hero_image_desktop`;
- `hero_image_mobile`;
- `hero_background_image`;
- `hero_video`;
- `hero_overlay_strength`.

Тогда можно:

- оптимизировать адаптив отдельно;
- не пытаться одной картинкой закрыть все экраны;
- проверять обязательность полей в зависимости от hero-стиля.

### SVG-иконки

Тут лучше не делать свободную вставку SVG каждым редактором.

Лучше два режима:

1. Выбор из библиотеки готовых иконок.
2. Вставка SVG только для продвинутых админов с sanitization.

Практически это можно реализовать как:

- модель `IconAsset` с `name`, `slug`, `svg_code`, `preview`;
- выбор иконки через autocomplete/select;
- рендер только через доверенный whitelist.

Так вы избежите хаоса и поломок.

### FAQ / раскрывающиеся списки

Для FAQ лучше отдельная дочерняя модель, а не одно большое текстовое поле.

Например:

- `LandingPageFaqBlock`
- `LandingPageFaqItem`

У `LandingPageFaqItem`:

- `question`
- `answer`
- `sort_order`

Плюсы:

- удобно редактировать;
- легко сортировать;
- можно автоматически генерировать `FAQPage` schema;
- фронтенд просто рисует accordion по готовым данным.

### Расположение блоков

Админ не должен задавать произвольные координаты.

Ему достаточно выбрать из безопасных вариантов:

- `image_left`
- `image_right`
- `centered`
- `two_columns`
- `three_cards`
- `sticky_side_card`

То есть расположение контролируется через `layout_variant`, а не через ручную верстку.

## Какая модель админки будет реально рабочей

Я бы строил её так:

### Уровень 1. LandingPage

Главная сущность страницы:

- общие SEO-поля;
- тема;
- статус;
- превью;
- связанные товары/категории/комплекты;
- действия: дублировать, открыть preview, открыть публичный URL.

### Уровень 2. LandingPageBlock

Список блоков страницы:

- `block_type`
- `sort_order`
- `is_active`
- `style_variant`
- `layout_variant`

Сортировка как у вас уже сделана в админке через `SortableInlineAdminMixin`.

### Уровень 3. Дочерние сущности блока

Для сложных блоков лучше отдельные inline-модели:

- FAQ items
- metric items
- comparison rows
- gallery slides
- CTA buttons

Тогда редактору не приходится редактировать большие JSON-массивы вручную.

## Как избежать дизайнерского хаоса

Если дать админу слишком много свободы, очень быстро появятся:

- разный стиль кнопок;
- несовместимые фоны;
- слишком длинные hero;
- плохие сочетания цветов;
- перегруженные секции;
- визуально "дешёвые" страницы.

Поэтому свободу надо дозировать.

### Что должно быть зафиксировано кодом

- ограниченный список тем;
- ограниченный список блоков;
- ограниченный список вариантов layout;
- ограниченный список стилей карточек;
- типографика;
- сетка;
- отступы;
- анимации;
- вид FAQ;
- вид CTA-кнопок.

### Что остаётся в руках админа

- тексты;
- изображения;
- подбор товаров;
- порядок секций;
- выбор готового варианта оформления секции;
- публикация / черновик;
- SEO-метаданные.

Именно в такой модели админ сможет быстро делать страницы без участия разработчика на каждую новую тему.

## Как должен выглядеть рабочий процесс редактора

Нормальный сценарий в админке:

1. Нажать "Создать SEO-страницу".
2. Выбрать шаблон страницы: `для дома`, `для клуба`, `для аттракционов`.
3. Заполнить SEO-поля и заголовок.
4. Выбрать тему страницы.
5. Загрузить hero media.
6. Отредактировать блоки шаблона.
7. Привязать 2-5 товаров и 1 комплект.
8. Заполнить FAQ.
9. Открыть preview.
10. Опубликовать.

Идеально, если будет ещё кнопка:

- `Дублировать страницу`

Это очень ускорит создание новых страниц под похожие интенты.

## Какие проверки система должна делать сама

Очень важно сразу добавить валидации, чтобы админ не публиковал слабые или поломанные страницы.

Проверки перед публикацией:

- есть `title`;
- есть `meta description`;
- есть `H1`;
- есть хотя бы один hero asset;
- есть хотя бы один CTA;
- есть хотя бы один контентный блок;
- если выбран FAQ block, в нём минимум 2 вопроса;
- если выбран product showcase block, в нём есть товары;
- если hero layout = `split`, то есть изображение;
- если страница B2B-типа, есть форма заявки или CTA на консультацию.

Можно даже сделать "оценку готовности страницы":

- 40% SEO
- 30% контент
- 20% коммерческий CTA
- 10% визуальное оформление

## Что я рекомендую для BizonVR конкретно

Для вашего проекта я бы делал не "свободный конструктор сайтов", а редактор шаблонных продающих страниц.

То есть:

- 6-10 типов блоков;
- 3-4 темы;
- 5-8 layout-вариантов;
- библиотека иконок;
- отдельные поля для hero media;
- FAQ как дочерние записи;
- product cards из реального каталога;
- preview в админке;
- дублирование страниц и шаблонов.

Такой подход даст сразу 3 плюса:

- админ сможет быстро собирать новые страницы;
- дизайн останется сильным и управляемым;
- разработчику не придётся вручную верстать каждый новый лендинг.

## Как использовать уже существующий код

В BizonVR уже есть элементы, которые можно переиспользовать, а не писать с нуля:

- sitemap-механизм в `config/sitemaps.py`;
- паттерн промо-страниц из `config/views/static_pages.py`;
- существующие каталожные карточки товаров и комплектов;
- блоковые описания товаров в `catalog.models.ProductDescription` и `ProductDescriptionBlock`.

Особенно полезная мысль: ваш текущий конструктор `ProductDescription` можно использовать как источник идей для структуры `LandingPageBlock`, но не стоит насильно смешивать "подробное описание товара" и "SEO-лендинг по теме".

Причина простая:

- у товара одна сущность;
- у SEO-лендинга часто несколько товаров, несколько интентов и маркетинговые блоки другого типа.

## Пример структуры одной страницы

Пример: `/solutions/vr-dlya-doma/`

1. Hero
2. Кому подходит домашний VR
3. 3 популярных сценария использования
4. Сравнение `Meta Quest 3`, `Quest 3S`, аксессуаров
5. Что купить сразу, чтобы не пожалеть
6. Готовый комплект
7. FAQ
8. CTA "Купить комплект" + "Получить консультацию"

Пример: `/solutions/vr-dlya-kluba/`

1. Hero для B2B-аудитории
2. Экономика и сценарий запуска
3. Какие форматы клуба бывают
4. Какое оборудование нужно
5. Рекомендуемые товары и комплекты
6. Кейсы / цифры / загрузка
7. FAQ
8. CTA на консультацию и подбор проекта

## Что я бы не рекомендовал

- Не делать это как обычный блог без связи с товарами.
- Не делать 50 почти одинаковых страниц под каждую вариацию запроса.
- Не тащить тяжёлый внешний CMS-движок, пока это можно решить внутри Django.
- Не хранить основной массив таких страниц вне БД как набор разрозненных папок.
- Не делать дизайн полностью одинаковым у всех страниц, иначе они будут выглядеть шаблонно и слабо конвертировать.

## Практический план запуска

### Первая волна страниц

Я бы начал с 6-8 страниц, которые имеют самый сильный коммерческий потенциал:

- VR для дома
- Лучшие VR-шлемы для дома
- VR для клуба
- Как открыть VR-клуб
- VR-аттракционы для мероприятий
- VR-аттракционы для ТЦ
- Готовый VR-комплект для старта
- Компактная VR-арена под ключ

### Контент-процесс

На одну страницу:

- 1 чёткий поисковый интент;
- 1 основной оффер;
- 1 главный CTA;
- 2-5 связанных товаров;
- 1 готовый комплект;
- 5-8 FAQ;
- 1 визуальная тема.

### Метрики успеха

Смотреть:

- индексируются ли URL;
- растут ли переходы из поиска;
- глубина просмотра после захода на страницу;
- CTR по CTA;
- переходы в карточки товара;
- добавления в корзину;
- заявки с таких страниц.

## Самый разумный следующий шаг

Если делать это правильно, я бы шёл так:

1. Спроектировать модель `LandingPage` и `LandingPageBlock`.
2. Сделать один базовый шаблон с 3-4 визуальными темами.
3. Выкатить 2 пилотные страницы: одна B2C и одна B2B.
4. Подключить их к sitemap, аналитике и связанным товарам.
5. После первых результатов масштабировать сетку контента.

## Что особенно важно для вашей задачи

Сильнее всего здесь сработает не просто SEO и не просто дизайн, а их связка:

- пользователь приходит на тему;
- получает визуально сильную, понятную, экспертную презентацию;
- сразу видит готовое решение;
- может или купить товар, или оставить заявку на подбор.

Для BizonVR это выглядит очень естественным расширением текущего каталога и существующих лендингов.
